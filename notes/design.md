# PWD 设计：把画面经 WiFi 送到 Pico W

> **一句话**：设备侧只做三件事 —— **收分片、组帧、解码上屏**；主机侧只做两件事 ——
> **把画面压成 JPEG、按分片协议发出去**。所有复杂度都在这两件事之间的**帧调度**上。
>
> **现状**：**M0 基线 ✓、M1 收帧统计 ✓、M2 v1（原始 RGB565 分带）✓** 都已达成；面板 = Z350IT008 ✓。
> **超频目前只到 240 MHz 档** ✗（300 MHz 起 CYW43 起不来，见 [`pico-turbo-overclock.md`](pico-turbo-overclock.md)）。

## TL;DR

- **传输**：UDP + 应用层分片；字段布局**沿用 P4 无线投屏那套**（PC 侧工具将来能两边通用）。
- **组帧策略**：只认**最新的完整帧**，缺片整帧丢并计数 —— 不重传、不无限等待。
- **设备侧只复用显示/解码库**（`pico-display-lib`）+ 移植 PUD 的流水线结论；
  **不复用 PUD 的 USB 端点协议**（那是另一条链路）。
- **判据来自设备自报的计数器**（收/丢/帧率/B/s），PC 侧另有一份独立统计，两边必须对得上。
- **时钟**：抬 `clk_sys` 会连带抬 `clk_peri`，而面板总线与 CYW43 的分频是**编译期按 125 MHz 算死的** ✗
  ⇒ 超频上限暂时 = 240 MHz（`safe` 档）✓，细节见 [`pico-turbo-overclock.md`](pico-turbo-overclock.md)。

## 数据流

```text
PC                                 Pico W (RP2040 + CYW43439)
──────────────                     ─────────────────────────────
 取画面 (ffmpeg / 截图)
      ↓ 编码 JPEG                    UDP 收分片
  分片 (≤1400 B)      ──WiFi──►       ↓ 按帧号组帧（缺片即丢整帧）
  发 UDP                               ↓ 帧槽（最新帧优先）
  统计（自报）                         ↓ 解码（JPEG 软解）
                                       ↓ 面板刷屏（pico-display-lib）
```

反过来（设备→PC）现在**不需要**：下行实测只有上行的 ~38%（见 `wifi-link-pico-w.md`），
而且投屏的瓶颈在"送到设备"这一侧。

## 传输协议（M1 定稿）

沿用 P4 无线投屏已经验证过的布局，**字段只追加、不重排、不复用编号**：

```text
每片 = [u32 帧号][u16 片序][u16 片数][u32 帧总长] + ≤1400 B 载荷
```

- **1400 B 载荷**：留出 IP/UDP 头，避免 IP 分片（实测 MTU 内的单包最省事）。
- **帧号**单调递增；设备侧只接受**当前帧号**与更新的帧号，旧帧的分片直接计入"过期丢弃"。
- **缺片的处理**：帧号前进就丢弃未完成的旧帧并计数 —— 显示端永远偏向"最新"，
  而不是"完整但过期"。一帧的片数由 `帧总长 / 1400` 上取整。

> 为什么不用 TCP：P4 上的实测是 TCP 114 fps / UDP + 丢帧策略 ~150 fps（同一套硬件条件）。
> Pico W 的上行只有 2.2 MB/s，30 fps @480×320 JPEG q85 只占 30% ⇒ **链路不是瓶颈时，
> 选行为可预测的那条**（UDP：丢帧可计数、延迟不累积；TCP：队头阻塞会把延迟越积越长）。

## 复用边界

| 复用 ✓ | 不复用 ✗ |
| --- | --- |
| `pico-display-lib`：面板驱动、SPI/PIO 总线、`tft_*_flush()`、输入 | PUD 的 USB 端点协议（EP1/EP2/EP4）、CherryUSB 栈 |
| PUD 踩过的**结论**：解码不在中断里、帧槽背压、缓冲区复用契约、看门狗自愈 | PUD 的定长帧槽尺寸（那是按 USB 的 64 KB 传输定的，RP2040 上不适用） |
| P4 无线投屏的 PC 侧 `pud_media.py`（ffmpeg → JPEG 参数映射）、分片发送端写法 | P4 的硬件 JPEG 解码路径（Pico W 没有硬件解码器） |
| `baseline/` 里官方例子的**构建配方**（wrapper + 凭据注入） | 官方例子的客户端模式源码（上游有 bug，见 `wifi-link-pico-w.md`） |

## 设备侧的关键约束（RP2040）

| 事实 | 影响 |
| --- | --- |
| RAM 只有 **264 KB**（RP2350 是 520 KB） | 帧槽不能照抄 PUD 的 64 KB；单帧缓冲 + 一块工作缓冲就够（JPEG 一帧约 22 KB） |
| **无 PSRAM** | 解码输出直接进面板窗口（band 刷屏），不做整屏 RGB565 缓冲（480×320×2 = 300 KB ✗） |
| CPU **125 MHz** 默认（SDK 时钟树） | JPEG **软解**是最大开销 ✗：RP2350@225 MHz 中位 69 ms ⇒ RP2040@125 MHz 外推 ~124 ms（~8 fps）✗ |
| 超频**暂时只到 240 MHz** ✗ | `fast`(300)/`turbo`(360)/`extreme`(440) 档下 CYW43 起不来 ✗（升频本身成功 ✓，坏在编译期分频 ✗）⇒ [`pico-turbo-overclock.md`](pico-turbo-overclock.md) |

## M2 v1：原始 RGB565 分带（已通 ✓）

**载荷 = 窗口头 + 原始像素**（分片头不动 ✓）：

```text
整帧载荷 = [u16 xs][u16 ys][u16 xe][u16 ye][RGB565 像素…]     （xe/ye 闭区间 ✓，小端 ✓）
```

- 一帧 = **一个带**（水平条带 ✓，默认 8 行 ⇒ 480×8×2 = 7680 B ⇒ 6 片 ✓）；一屏 = 40 带 ✓。
- 设备侧：组好的带在主循环里 `tft_video_flush()` 上屏 ✓（**不在 lwIP 回调里做** ✗ —— 走总线要等硬件 ✓）；
  中断侧只组帧，用 take/release 交接缓冲区 ✓。
- **v1 不解码**（原始像素直通 ✓）：全屏 300 KB/帧 ⇒ 上行 2.2 MB/s 下理论 ~7 fps ✓；实测
  **40 带/s（= 1 整图/s）干净** ✓，更高速率待测 ✓。**下一步是 JPEG 流** ✓（不是 QOI ✗，理由见下节）。

**踩过的坑（都有真机指纹 ✓）**：

| 现象 | 根因 |
| --- | --- |
| 2.5 Mbit/s 就丢**一半分片** ✗ | lwIP 的 pbuf 池太小（官方例子的公共 lwipopts 是给轻流量调的 ✗）⇒ 在 `src/lwipopts.h` 里 `#undef` + 放大 `PBUF_POOL_SIZE`/`MEMP_NUM_PBUF` 后，**5.33 Mbit/s 下 1600 片零丢** ✓ |
| 一轮 40 带**全速连发**时丢 ~50% ✗ | 突发打爆对端接收 ⇒ 发送端改成**逐带限速** ✓（`--band-fps` ✓） |
| 固件 **HardFault**（PC 落在库的 `tft_video_flush` ✓） | `on_frame_complete()` 结尾 `reset_assembly()` 把 `s_frame_len` **清零** ✗，主循环随后读到 0 ⇒ 传给库的长度 = `0-8 = 0xFFFFFFF8` ⇒ 库去写 4 GB 像素 ✗。日志指纹：`[panel] ✗ 拒带 … len=4294967288` ✓。修法：长度单独存 `s_ready_len` ✓ |
| 越界窗口 | 兜底检查放在**我们这层** ✓（库的接口不做范围校验 ✗）——它正是靠这条把上面那个 4 GB 写拦下来的 ✓ |

## M3：编解码选型 —— **JPEG 流** ✓（不是因为 QOI 不好，是因为链路放不下 ✗）

| 编解码 | 载荷/帧 | 30 fps 需要 | 设备侧解码 | 结论 |
| --- | --- | --- | --- | --- |
| **JPEG q85** | **≈22 KB** | **0.66 MB/s** ✓ = 上行 2.2 MB/s 的 **30%** ✓ | RP2350@225 MHz 实测 **median 69 ms** ✗（15 fps）⇒ RP2040@125 MHz 外推 ~124 ms ✗ | **链路轻、CPU 重** ⇒ 用 ✓，**但要超频** ✓ |
| QOI（无损） | 真实桌面整屏 **76 503 B** ✓（PUD `notes/codec-selection.md` ✓；高熵内容更差 ✗） | **2.3 MB/s** ✗ ≈ 上行的 **105%** ✗ | 约 **6 ms** ✓（由 PUD 那句"三者都跑在链路极限上"反推 ✓） | **CPU 轻、链路重** ✗ ⇒ 流式用不了 ✗ |

**出处**：JPEG 载荷来自本仓 `README.md` 的链路预算（PUD/P4 侧实测 ✓）；QOI 载荷与"链路极限"结论来自
`../Pico-USB-Display/notes/codec-selection.md`（PUD 的 USB 链路 ≈1.1 MB/s 下实测 ✓）；JPEG 解码耗时来自
`../Pico-USB-Display/notes/decoder-architecture.md`（225/366/520 MHz 三档 ✓）。

**重要区分**：QOI"不受限"指的是**CPU**（解码几乎不花时间 ✓），**不是链路** ✗ —— 它的载荷在这个
2.2 MB/s 的上行上 30 fps 放不下 ✓。

**M3 路线** ✓：PC 侧 ffmpeg → JPEG q85（≈22 KB/帧 ✓，复用 P4 无线投屏的 `pud_media.py` ✓）→
设备侧软解 → 走已有的分带/上屏路径 ✓。**解码库选型未定** ✗（PUD 用的是 vendored `tjpgd` ✓；
用户提过 JPEGDEC 效率更高，但**本仓未验证** ✗）；动手前先量一件事 ✗：RP2040 在 125/240 MHz 下
解 480×320 JPEG 的**单帧耗时** ✓。

## 面板与触摸：Z350IT008（ILI9488 驱动 + GT911，8080 16-bit）

| 项 | 事实 | 凭据 |
| --- | --- | --- |
| 面板模块 | **Z350IT008**（用户按屏上丝印确认 ✓），屏幕驱动 = **ILI9488** ✓，触摸 = **GT911** ✓；8080 16-bit 并口 | ⚠️ 之前按 "YT350S006 / ST7796" 配过 ✗ —— 那是**记错型号** ✗，屏幕全白 ✗；换 ILI9488 后立刻点亮 ✓ |
| 初始化序列 | **必须用 Z350IT008 自己那套** ✓（伽马/帧率/VCOM 与库默认的 QD3503728 那套都不同 ✗，用错色彩就不对 ✗） | 照 `pico_dm_8080_template/src/tft_ili9488.c` 的 `TFT_MODEL_ZT350IT008` 支逐条抄 ✓；库里做成 `TFT_ILI9488_VARIANT_ZT350IT008` ✓ |
| 触摸 | **GT911**（I2C，含 IRQ/RST）；配置里暂 `INDEV_DRV_NOT_USED 1` ✓，先只做面板 ✓ | PUD 的 `configs/pico_dm_ep4309n.cmake` 是现成的 GT911 写法 ✓ |

**实际接线**（2026-10，用户接线表 ✓）：数据 `D0..D15 = 0–15`、`WR 19`、`RS 20`、`RST 22`、
**`CS` 不接（硬件下拉 ✓）**、背光 `BLK 28` ✓（实测：改到 27 时用户报"背光都不亮" ✓）、
触摸 `CTP_RST 18` / `CTP_IRQ 21` / I2C `SDA 26` / `SCL 27` ✓。

- **这不是 ILI9488 模块那套** ✗：PUD 的 8080 模块用 `CS 18` ✓，而本模块的 **18 是触摸复位** ✗
  ⇒ 照抄同系列模块 = 每写一次像素就乱动一次触摸复位 ✗，背光脚也抄错了 ✗。**接线表必须逐脚核对** ✗。
- 库的 i80 路径每次写都动 `CS+RS`（`i80_set_rs_cs()` ✓），**没有"CS 不接"的开关** ✗
  ⇒ 给一个空闲脚当占位：**GP16** ✓（代价 = 固件调试串口让位，改只走 USB stdio ✓）。
  不能给 18/21/26/27/28 ✗（触摸与背光在上面）。
- 落地：**`lib/pico-display-lib/configs/pico_dm_z350it008-8080.cmake`** ✓（面板配置的归属地是那个库，
  本仓 `configs/` 与 PUD 一样是**指向它的软链接** ✓），用 `-DPUD_CONFIG=pico_dm_z350it008-8080` 选 ✓；
  几何 = 原生 320×480 + rotation 1 ⇒ 逻辑 480×320 ✓。

与 PUD 那份同模块 SPI 配置的差异（"16 位并口 + 本模块接线"的必然后果 ✓）：
`TFT_BUS_TYPE 0→1` ✓、`TFT_COLOR_16_SWAP 1→0` ✓（16 位总线上换字节会错色 ✗）、背光 `13→28` ✓、
总线时钟 `100→25 MHz` ✓（bring-up 先降；125 MHz CPU 下 50 MHz 总线会让 PIO 占用率到 ~80% ✗）、
`OVERCLOCK_ENABLED 0` ✓（先关，一次只动一个变量）。

**Pico W 的引脚约束** ✓（`boards/pico_w.h` 的 `CYW43_DEFAULT_PIN_*`）：
`WL_REG_ON 23`、`WL_DATA_* 24`、`WL_CS 25`、`WL_CLOCK 29` ⇒ **23/24/25/29 不可用**；
剩 0–22、26–28 共 **26 个**要装下 16 数据线 + `WR/RS/RST` + 背光 + 触摸 I2C（+ IRQ/RST）⇒ **排布很紧** ✗。

## 已定项与 UNKNOWN

**已定** ✓：① 传输 = UDP + 分片，只用最新完整帧；② 显示/解码以 `pico-display-lib` 为基础，不重写面板驱动；
③ M0 基线 = 官方 `pico_w/wifi/iperf`（本仓 `baseline/`，零 delta）；④ 面板 = Z350IT008 + ILI9488 专属初始化序列 ✓；
⑤ 超频接入 `lib/pico-turbo`，**默认档钉在 `safe`（240 MHz）** ✓。

**UNKNOWN** ✗（要用硬件/实测回答，不许猜）：

| 问题 | 为什么必须先问 |
| --- | --- |
| RP2040 @125/240 MHz 解 480×320 JPEG 的**单帧耗时**？ | 决定 M3 的帧率上限，也决定"要不要把超频那条线修好" ✓ |
| 300/440 MHz 档能不能修好（`clk_peri` 分频 / CYW43 PIO 分频）？ | 修好前只能跑 240 MHz ✗；修法未定，见 [`pico-turbo-overclock.md`](pico-turbo-overclock.md) |
| CYW43439 在 2.2 MB/s 持续 UDP 下的**长时**丢包率？ | M1 的"100 帧/1600 片零丢" ✓ 只覆盖 ~20 秒短程 ⇒ 长时稳态未测 ✗ |
